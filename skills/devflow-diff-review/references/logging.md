# Журнал ревью

Конфиг: `~/.devflow/config.json`, ключ `review_logs_root` — абсолютный путь
или путь с `~`. При отсутствии или ошибке настройки сообщи причину;
не выбирай незаметно другой каталог.

Создай журнал командой `python3 <папка-скилла>/scripts/init_review_log.py --pr <ID>`.
Для локального diff без PR опусти `--pr`. Команда возвращает путь к новой папке
`PR-<ID>-<UID>` или `DIFF-<UID>`; UID числовой. Новый запуск всегда получает
новую папку. Прерванный запуск продолжай в его папке только после сверки предмета,
версии и завершённых этапов; смена проверяемой версии требует нового запуска.
Скрипт сохраняет в `run.json` исходные тексты и хеши инструкций, включая файлы линз.

| Файл | Кто пишет и что сохраняет |
| --- | --- |
| `run.json` | Координатор: исходный запрос, репозиторий, точный base/head или snapshot, общий контекст и назначения; фактические участники, модели, статусы, время и доступные затраты. |
| `bugs.md`, `impl.md`, `architecture.md`, `quality.md`, `docs.md`, `tests.md`, `comments.md`, `adversarial.md`, `deployment.md` | Назначенный ревьюер: исходные находки своей линзы, основания, проверенные области и ограничения. |
| `validation.md` | Координатор сохраняет фактически передаваемые кандидаты до вызова валидатора; валидатор дописывает решения и основания по их ID. |
| `result.md` | Координатор: самодостаточный отчёт, выведенный в чат; затем приложение со связью исходных кандидатов с принятыми, объединёнными, отклонёнными и неразрешёнными пунктами. |

Перед запуском участников заполни запрос, snapshot, общий контекст и фактические
назначения в `run.json`; `context` включает переданные инструкции и ссылки
на источники. Ревьюеры пишут только свои файлы и не читают чужие выводы
до завершения независимого прохода. Валидатор читает исходные результаты;
координатор использует их для сведения без пересказа задним числом.

У каждого кандидата — устойчивый ID внутри запуска, например `bugs-impl:1`,
и конкретные линзы-авторы. Одна находка нескольких линз одного агента сохраняет
один ID; одинаковые находки разных агентов сохраняют исходные ID при объединении.
Каждый исходный кандидат должен прослеживаться через валидацию до итога.
Сохраняй первоначальные отчёты; уточнения и пересмотры дописывай с причиной.

В файле линзы различай `pending`, `completed`, `not_applicable` и `unavailable`.
`completed` без находок означает выполненную проверку. Для завершённых этапов
запиши фактическое время; недоступные значения оставляй `null`.
Модели и расход учитывай по агентам, а не по линзам одного агента; различай
запрошенную модель и подтверждённую средой. Не оценивай неизвестные затраты.

Координатор завершает `run.json`: `completed` при полном журнале выбранного
объёма, `partial` при ограничениях или `interrupted` при остановке.
`running` без завершения также означает незавершённый запуск. Для адресного
повторного ревью укажи `mode: targeted`, выбранные проходы и предыдущий запуск;
не выполнявшиеся в этом объёме проходы обозначь `not_requested`.
При ошибке записи сохрани доступный результат и явно сообщи неполноту.

Это проверяемые результаты и история решений, а не полный дамп сессии.
Сохраняй достаточные основания и ссылки, без секретов и лишних чувствительных данных.
